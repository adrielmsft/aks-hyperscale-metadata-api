## Background
You are to implement a metadata API server. This is simply an API to manage two distinct resources: Application and Maintainer. Maintainers are users that manage Application. They can perform operations on these applications such as creation, deletion, get, and update. Maintainers can themselves are managed via the same operations. For this project, we will be using ASP.NET and C#.

## Scope
A RESTful HTTP API that enables CRUD operations for Application and Maintainer resources and management of their many-to-many associations. Both resources receive server-generated IDs. Maintainers are contact metadata, not authenticated identities. A single configured API key grants clients administrative access to all resources; per-maintainer authorization is out of scope.

### Data Model Input Validation

Validation is performed at the API boundary before writing data. Required fields must be present and non-null on creation and full replacement (PUT). Optional fields may be omitted or set to null; omitted optional fields on PUT are cleared. PATCH is out of scope.

#### Common rules

- Trim leading and trailing whitespace from text fields before validation and storage. Preserve internal whitespace and casing.
- Required strings must not be empty or whitespace-only after trimming. Normalize empty optional strings to null.
- Length limits below are measured using .NET string length (UTF-16 code units) after trimming.
- Reject control characters in single-line fields. Description may contain line breaks and tabs, but no other control characters.
- IDs are server-generated, non-empty GUIDs and are immutable. Create and update request models exclude resource IDs; reject an `id` property rather than silently ignoring it.
- Route IDs and association IDs must parse as non-empty GUIDs. A valid ID does not imply that the referenced resource exists.
- Accept only documented JSON properties and types; reject unknown properties to catch client typos.
- Names, titles, and email addresses are not unique identifiers. Duplicate values are allowed; identity is determined by the resource ID.

#### Maintainer

| Field | Required | Validation |
| --- | --- | --- |
| Name | Yes | 1-200 characters. Allow Unicode, spaces, apostrophes, and hyphens; do not impose an ASCII-only or first-name/last-name pattern. |
| Email | Yes | At most 254 characters. Use .NET's `EmailAddressAttribute` for basic syntax validation rather than a custom regex. Accept an address only, not a display-name form such as `Alex <alex@example.com>`. Do not perform DNS checks or send verification email. |

Email validation checks syntax only; it does not establish ownership or deliverability. Maintainer email addresses are contact metadata, not login identities.

#### Application

| Field | Required | Validation |
| --- | --- | --- |
| Title | Yes | 1-200 characters. Allow human-readable Unicode text; titles need not be unique. |
| Version | No | When supplied, at most 100 characters. Follow Semantic Versioning 2.0.0: `major.minor.patch`, optionally followed by prerelease and build metadata, for example `1.2.0`, `2.0.0-rc.1`, or `1.2.0+build.7`. Reject a `v` prefix, missing components, and leading zeros in numeric core or numeric prerelease components. |
| Company | No | At most 200 characters. |
| Website | No | At most 2,048 characters. An absolute HTTP or HTTPS URL with a non-empty host and no embedded username/password. |
| Source | No | Same URL rules as Website. Represents a source repository or source-code location; private repositories are allowed. |
| License | No | At most 100 characters. Prefer an SPDX identifier such as `MIT`, `Apache-2.0`, or `BSD-3-Clause`. Allow `Proprietary` as an application-specific convention. Validate length and single-line text only; SPDX registry membership and expression parsing are out of scope. |
| Description | No | At most 4,000 characters. Plain text, not interpreted as HTML. |

For URL fields, use `Uri.TryCreate` with `UriKind.Absolute` and explicitly check the scheme, host, and user information. Do not fetch URLs or check reachability: validation must not depend on external services or make server-side requests to client-supplied locations. A null License means "not provided"; it does not imply permission to use the software.

#### ApplicationMaintainer

- Both ApplicationId and MaintainerId are required, non-empty GUIDs.
- Both referenced resources must exist before an association can be created.
- Enforce a composite primary key on `(ApplicationId, MaintainerId)` and foreign keys to both resources in storage, not just API-level checks.
- Repeating an association PUT leaves the existing association unchanged rather than creating a duplicate.
- Deleting an application or maintainer removes its association rows, but never deletes the resources on the other side.
- Applications and maintainers may have zero associations; there is no minimum-maintainer requirement.

#### Validation errors

- Return `400 Bad Request` for malformed JSON, invalid field values, unsupported properties, or malformed/empty GUIDs.
- Return `404 Not Found` when a syntactically valid resource ID does not exist, including either resource referenced by an association.
- Use ASP.NET Core Problem Details with a field-keyed `errors` object for validation failures. Report all detected field errors together, without echoing submitted values or exposing exception details.

Example validation response (`Content-Type: application/problem+json`):

```json
{
  "type": "about:blank",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": {
    "email": ["Email must be a valid email address."],
    "name": ["Name is required."]
  }
}
```

Tests should cover missing/null/blank required fields, exact length boundaries and one character beyond, malformed and empty GUIDs, valid Unicode names, valid and invalid semantic versions, rejected URL schemes and embedded credentials, unknown JSON properties, nonexistent association targets, and repeated association creation.

## API Design

### Conventions

- Base path: `/api/v1`. Versioning applies to the API contract, independently of an application's Version field.
- Use plural resource names and GUID identifiers, never names or titles, in resource paths.
- All resource endpoints require `Authorization: Bearer <API_KEY>`. Missing or invalid credentials return `401 Unauthorized` with `WWW-Authenticate: Bearer`.
- Request and response bodies use JSON with camelCase property names. Optional resource fields are returned explicitly as null when not provided.
- POST creates a resource and returns `201 Created`, its representation, and a `Location` header pointing to its GET endpoint.
- PUT replaces an existing resource's editable fields and returns `200 OK` with the updated representation. It does not create a missing resource or change its ID or associations.
- Resource DELETE returns `204 No Content`; a missing resource returns `404 Not Found`, including on repeat deletion. Repetition remains idempotent because the resulting state is unchanged.
- PATCH, bulk operations, search, and create-request idempotency keys are out of scope. Updates initially use last-write-wins; optimistic concurrency is not part of this API contract yet.

### Application-maintainer associations

Applications and maintainers may each have zero or more associations. Manage links independently of resource creation; there is no separate association ID or top-level association CRUD API.

| Method | Path | Behavior | Success |
| --- | --- | --- | --- |
| PUT | `/api/v1/applications/{applicationId}/maintainers/{maintainerId}` | Ensure the association exists. No request body; repeated calls do not create duplicates. | 204 |
| DELETE | `/api/v1/applications/{applicationId}/maintainers/{maintainerId}` | Ensure the association is absent without deleting either resource. No request body. | 204 |
| GET | `/api/v1/applications/{applicationId}/maintainers` | List associated maintainer resources with pagination. | 200 |
| GET | `/api/v1/maintainers/{maintainerId}/applications` | List associated application resources with pagination. | 200 |

Association PUT and DELETE require both resources to exist; otherwise return 404. If both exist but the link is already absent, association DELETE returns 204. Nested list endpoints return 404 for a missing parent and an empty page for an existing parent with no associations. Enforce association changes atomically with database constraints.

### Pagination

All four list endpoints accept `limit` (default 20, range 1-100) and `offset` (default 0, range 0-10,000). Invalid, non-integer, or out-of-range values return 400 rather than silently being clamped.

Order results by the returned resource's ID ascending using database ordering. Return at most `limit` items and fetch one extra row to determine whether more exist. Responses use this envelope:

```json
{
  "items": [
    {
      "id": "54b28c61-8ec5-42c1-966b-3564c59bf965",
      "name": "Adriel Kim",
      "email": "adrielkim@microsoft.com"
    }
  ],
  "limit": 20,
  "offset": 0,
  "nextOffset": null
}
```

`nextOffset` is `offset + limit` only when more results exist and that offset is within the supported range; otherwise it is null. Empty pages return `items: []`. Pagination is not a snapshot: concurrent writes may shift results. Offset pagination and its traversal cap are deliberate small-system trade-offs; larger catalogs would use cursor pagination.

### Error contract

Errors use `application/problem+json` and Problem Details, with field-keyed `errors` for validation failures as shown above.

| Status | Meaning |
| --- | --- |
| 400 Bad Request | Malformed JSON, invalid fields or query parameters, unknown properties, or invalid/empty GUIDs. |
| 401 Unauthorized | Missing or invalid API key; does not reveal whether a resource exists. |
| 404 Not Found | A resource or required association target does not exist. |
| 405 Method Not Allowed | A route exists but does not support the HTTP method; include an Allow header. |
| 415 Unsupported Media Type | A body-bearing resource POST or PUT request does not use a supported JSON content type. |
| 500 Internal Server Error | Unexpected failure; return a generic message and log details server-side without credentials. |
| 503 Service Unavailable | Database lock contention exceeded the bounded wait; the write did not succeed. |

## Storage Layer

Use **file-backed SQLite with EF Core**, targeting one API instance on one machine. This provides relational constraints and transactions without a separate database service. Prioritize correctness, consistency, and durable commits over write throughput.

```text
API endpoints -> Application services -> EF Core DbContext -> SQLite file
```

Endpoints own HTTP concerns; services coordinate workflows and transactions; persistence code owns EF Core queries and mappings. No additional generic repository is needed.

### Integrity and configuration

- Use GUID primary keys on Applications and Maintainers. Use a composite primary key `(ApplicationId, MaintainerId)` and foreign keys on ApplicationMaintainers; cascade deletion to association rows only. Add an index on MaintainerId for reverse lookups.
- Enable `foreign_keys=ON` and `synchronous=FULL` on every connection. Initialize and verify `journal_mode=WAL` before serving requests. Fail startup explicitly if required settings cannot be established.
- WAL permits readers alongside a writer; FULL synchronizes the WAL at each commit to favor power-loss durability, subject to the filesystem and hardware honoring synchronization.
- Make related changes atomic using transactions. A single EF Core SaveChanges call is transactional; use an explicit transaction for workflows spanning multiple saves. Keep transactions short.
- Validate field rules before persistence; SQLite does not automatically enforce declared string length limits.
- Configure a five-second database lock-wait timeout, with no unbounded application retries. Return Problem Details with 503 when lock contention exhausts the wait; roll back failed transactions and never report a failed write as successful.
- Updates retain the current last-write-wins contract. Transaction integrity does not prevent stale clients from overwriting newer values; optimistic concurrency remains a separate potential feature.

### Persistence and lifecycle

- Use a configurable, stable database path on persistent local storage. Reopen the same file after restart; never delete or recreate it during normal startup. Exclude database, WAL, and shared-memory files from Git.
- Apply versioned EF Core migrations through a documented command before starting the server, both locally and in CI. Use isolated temporary databases for tests.
- Persistence is not a backup. Document a SQLite-supported backup procedure rather than copying only the main file while WAL is active; automated backup infrastructure is out of scope.

### Limits and verification

SQLite allows one writer at a time. Use indexed queries and bounded database-side pagination; distributed operation and shared database files on network storage are out of scope. If write contention or multiple API replicas become requirements, migrate to PostgreSQL or SQL Server with provider-specific migrations, data transfer, and regression testing.

Test against real SQLite: verify configured settings, foreign keys, duplicate-link prevention, cascading link deletion, rollback on failure, bounded lock contention, and persistence across server restart.

## Production Readiness

- **Standout feature: observability.** Use structured logging and OpenTelemetry for request traces and metrics (request count, duration, active requests, and rate-limit rejections). Support optional OTLP export to an external collector without requiring a dashboard or backend to run the API. Correlate logs with trace IDs and demonstrate export with a collector smoke test; highlight this feature in the README.
- **Telemetry safeguards:** never record API keys, request bodies, or maintainer emails. Use route templates rather than resource IDs as metric labels. Bound telemetry queues; exporter failures must not fail API requests, and diagnostic reporting must not leak credentials.
- **Authentication:** require the configured shared API key on resource endpoints. Store it outside source control; missing or invalid credentials return 401. Authenticated clients have administrative access, not per-maintainer permissions. Require HTTPS when publicly deployed.
- **API contract:** use `/api/v1` for explicit contract versioning and publish an OpenAPI specification. Supporting multiple API versions is out of scope.
- **Failure handling:** use centralized exception handling with generic Problem Details responses and server-side diagnostics correlated by trace ID. Keep expected validation and not-found responses distinct from unexpected failures; never expose stack traces or database details to clients.
- **Contention and retries:** retain the bounded database lock wait and 503 response defined above. Do not add blanket write retries: replaying POST can create duplicates. Transactions and SQLite synchronization settings provide durability, not retries.
- **Throttling:** use ASP.NET Core's built-in rate limiter with a configurable, documented global request limit and no queue. Return 429 Problem Details and `Retry-After` when available. This protects the single instance but does not provide per-user fairness.
- **OOM prevention:** cap request-body size before JSON deserialization, return 413 for oversized bodies, and retain bounded database-side pagination and telemetry buffering. These reduce memory-exhaustion risk; catching OutOfMemoryException is not a recovery strategy.
- **Explicit exclusions:** no dashboard, alerting infrastructure, distributed rate limiting, or optimistic concurrency in the initial scope. Updates use last-write-wins: stale PUT requests can overwrite newer metadata. Database transactions protect integrity but do not prevent lost updates.

## Testing

Use **xUnit** for all test suites, `dotnet test` as the runner entry point, and **GitHub Actions** for CI. Use built-in xUnit assertions and HttpClient; add mocking libraries only if a concrete need arises.

### Unit tests

- Test field validation and normalization, optional/null handling, length boundaries, semantic versions, URL rules, and pagination parameters.
- Keep these tests independent of HTTP hosting, database files, and external services.
- Collect coverage using Coverlet with a compatible .NET test runner configuration. Publish unit-test coverage in the CI summary and upload the report; no minimum threshold is required.

### Storage integration tests

- Exercise EF Core against real SQLite, not EF Core's InMemory provider.
- Use isolated temporary file-backed databases and the same migrations and connection configuration as the API.
- Verify foreign keys, unique association pairs, cascading link deletion, transactional rollback, configured SQLite settings, bounded lock waits, and persistence after reopening the database.
- Clean up database connections and temporary files after each test fixture. Explicitly control parallel execution for contention tests.

### E2E tests

- Start the built API as a separate process on localhost with a temporary database and test-only API key. Use HttpClient to test real HTTP requests without mocking the server or storage.
- Cover CRUD for both resources, association creation/removal and repeated PUT, deletion integrity, pagination, validation errors, authentication, body-size limits, and rate limiting.
- Verify status codes, response shapes, Location headers, and Problem Details, not just successful responses. Restart the API against the same database to verify persistence.
- Include a focused smoke test against a local OpenTelemetry collector to verify exported telemetry and trace correlation, without requiring a cloud account or dashboard.
- Isolate test resources and serialize scenarios that share server-wide state, such as rate-limit tests. Use readiness checks and bounded waits rather than fixed startup sleeps.

### GitHub Actions pipeline

Run on pushes and pull requests:

```text
Restore -> Build -> Unit/storage tests + coverage
        -> Apply migrations -> Start API and local telemetry collector
        -> Wait for readiness -> E2E tests
        -> Publish results and clean up
```

- Pin the .NET SDK version and document commands for running the same suites locally.
- Generate an ephemeral API key for CI, mask it in logs, and never commit it. No production credentials are required.
- Fail the pipeline on build or test failures. Upload test results, coverage, and sanitized diagnostic logs, including on failure; always stop started processes and clean up temporary databases.
- Before submission, ensure at least one successful E2E workflow run is publicly visible and link directly to that run from the README.
